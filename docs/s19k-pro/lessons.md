# Debugging lessons

Traps hit during this work. Several cost hours. They generalise
beyond this hardware.

## Sanity-check the measurement before building theories on it

The single most expensive mistake here.

`Difficulty`'s `Display` implementation uses SI suffixes — values
≥ 1000 render as `1.5K`, `112K`, `1.2M`. A log filter of
`hash_diff=[0-9.]+` silently captures the mantissa and **drops the
suffix**, turning a difficulty of 45,600 into `45.6`.

That produced a clean-looking, entirely false finding: *"maximum
observed difficulty is capped just under 1,000, across 25,000
samples."* Two separate root-cause theories were then built on top of
it — a `TicketMask` filter ceiling, then redundant nonce-space search
— and real hardware time was spent testing both.

The tell was there: every run topping out at 954, 968, 983, 987, 995
is a suspiciously tidy distribution for a stochastic process. That
pattern should prompt *"is my instrument broken?"* before *"what is
the hardware doing?"*

**Rule:** when data looks structurally odd rather than merely
surprising, verify the measurement path first. It is cheaper than a
hardware test and it is more often the culprit than you expect.

## Distrust telemetry that could be a constant

The API's per-thread `hashrate` is `83 GH/s × chip_count`, assigned
once in the constructor and never recomputed from real nonces. It
reports 6.39 TH/s per board whether the board is doing 2 TH/s or
85 TH/s.

Before trusting a number, find where it is produced. "Is this
measured, or is it declared?" is a fast, high-yield question.

## Check log filters against the emitting module's level

Several "this code path never executes!" conclusions turned out to be
`RUST_LOG` targeting mistakes:

- `handle_share`'s stale-task early return is `trace!`, so it is
  invisible at `debug`.
- The scheduler's `"Share found"` is under `mujina_miner::scheduler`,
  not `asic::bm13xx` — filtering the latter shows nothing regardless
  of what happens.

Absence of a log line is evidence about **your filter** until you've
confirmed the line is enabled and reachable.

## Beware diagnostics that test the wrong layer

A probe swept 100–600 MHz writing `PllDivider` and re-running
discovery at each step, reporting clean 77/77 chips at every
frequency. That looked like proof that high frequencies were fine.

It only proved the chain still **addresses** cleanly. It said nothing
about whether the PLL reached a working lock, or whether any core was
hashing. It gave false confidence for several rounds.

**Ask what a passing test actually excludes.** "Communication
survived" and "the hardware is doing useful work" are very different
claims.

## Reading source beats reasoning from symptoms

Every hypothesis generated by staring at symptoms was wrong:
`NonceRange` partitioning, `TicketMask` capping, job-ID bit widths,
PLL lock failure, a share-submission plumbing bug.

The actual bug was found in about an hour by systematically comparing
the reference implementation against real captured wire bytes,
register by register — specifically by diffing `bm1366()` against
`bm1370()`, which made the discrepancy obvious.

When symptom-driven hypotheses keep failing, that is a signal to
switch mode entirely, not to generate more hypotheses.

## Verify claims before acting, including your own

Several "smoking guns" in this work were announced and then had to be
walked back after actually reading the code — the `NonceRange` value,
the `TicketMask` setting, the job-ID bit packing. Each looked
compelling from a grep.

Both real fixes that survived (`Core` byte order, the strict
post-divider constraint) were confirmed by reading the encoder and
doing the byte arithmetic by hand before any hardware test.

## Change one thing at a time — and revert failed changes

Two changes made during debugging were themselves regressions:

- Replacing the broadcast `NonceRange` with a "partitioned"
  chain-length-keyed value. It selected the **S21 Pro** constant for
  a 77-chip chain and discarded the correct captured BM1366 value.
  Real firmware broadcasts a single value here and still reaches
  ~39 TH/s.
- Forcing the suggested pool difficulty up to a known-good figure,
  which made qualifying shares ~14× rarer and *hid* evidence rather
  than producing it.

Both were reverted before the decisive test. Carrying failed
experiments forward makes the next result uninterpretable.

## A passing test can be asserting the wrong thing

The `Core` byte-order bug was covered by a unit test that asserted
`to_le_bytes()` for a register encoded with `put_u32` (big-endian).
The test passed on the reversed values, so CI stayed green over a
~50× hashrate defect.

A test that encodes the same misunderstanding as the code validates
nothing. Where wire format matters, assert against **captured bytes
through the real encoder**, not against a re-derivation.

## Hardware-specific operational notes

- **Stale monitoring reads like healthy monitoring.** The fan-RPM
  metrics file only updates while `bosminer` runs; stop it and the
  file silently freezes at plausible values. *Always check the
  timestamp, not just the value.*
- **A burst of pool rejects after a hashrate change is expected**,
  not a defect — vardiff moves and in-flight shares miss. Split
  rejects chronologically before investigating.
- **Watch for concurrent instances.** One accidental second process
  contended on the bit-banged PSU GPIO lines and corrupted a test's
  voltage mid-run. Verify no prior instance survives before starting
  another.
- **Efficiency is a good completeness check.** Landing at ~23 J/TH
  against a 23.0 J/TH nameplate was strong evidence the fix was
  complete rather than partial. A partial fix would show a plausible
  hashrate at implausible efficiency.
